# Веб-онбординг з оплатою

Онбординг: телефон → email → квіз → вибір тарифу та оплата через Stripe (test mode) → success.
Порядок екранів приходить з бекенда (`GET /flow`).

- `frontend/` — React 19 + TypeScript (strict) + Redux Toolkit + React Router + styled-components + Vite
- `backend/` — готовий API поверх Stripe (не змінювався)

**Демо:** https://onboarding-web-chi.vercel.app · **API:** https://onboarding-test-task.vercel.app

## Запуск локально

Потрібні Node.js **22.9+** (бекенд використовує `--env-file-if-exists`) і тестові ключі Stripe.

```bash
# 1. Бекенд — http://localhost:4242
cd backend
npm install
cp .env.example .env        # вписати sk_test_… і pk_test_…
npm run dev

# 2. Фронтенд — http://localhost:5173
cd frontend
npm install
cp .env.example .env        # VITE_API_URL=http://localhost:4242 (це і так значення за замовчуванням)
npm run dev
```

Інші флоу: `http://localhost:5173/?flow=short`, `?flow=experimental` (у ньому є невідомий екран `promo`, він пропускається).

Скрипти фронтенду: `npm run build`, `npm run typecheck`, `npm run lint`, `npm run format`.

### Тестові дані

| Сценарій | Що ввести |
|---|---|
| Картка без 3DS | `4242 4242 4242 4242` |
| 3DS, успіх / відмова | `4000 0027 6000 3184` → у вікні «Complete» / «Fail» |
| Відмова картки | `4000 0000 0000 0002` |
| Редірект | будь-який метод для EUR, увімкнений у Dashboard (iDEAL, Bancontact, EPS…) → на сторінці Stripe «Authorize» / «Fail» |

Будь-яка майбутня дата, будь-який CVC. Більше: https://docs.stripe.com/testing

## Структура

```
frontend/src/
├── app/            Збирає застосунок: store, збереження стану, роутер, провайдери
├── flow/           «Двигун» онбордингу: флоу з бекенда, кроки, гарди, навігація
├── screens/        Один екран = одна папка + registry.ts (список відомих екранів)
├── features/       Доменний стан і логіка, яку використовують екрани
│   ├── profile/      телефон, email, валідація
│   ├── quiz/         відповіді квізу + спільний компонент QuizStep
│   ├── plans/        тарифи з бекенда
│   └── payment/      стан оплати, Stripe, idempotency, перевірка статусу
└── shared/         Нічого не знає про домен: API-клієнт, UI-кіт, тема, i18n, аналітика
```

**Правило залежностей:** `app → flow → screens → features → shared`. `shared` не імпортує нічого
з верхніх шарів, `features` не знають про конкретні екрани, екрани не знають один про одного.

Чому так:

- **Екран не знає, хто після нього.** Він викликає `goNext()` з `useFlowNavigation`. Наступний крок
  визначає `flow/` за списком із бекенда.
- **Роутер не перелічує екрани.** Є один динамічний маршрут `/:stepPath`, і `StepRoute` за реєстром
  знаходить потрібний екран. Тому новий екран не потребує змін у роутингу.
- **Доступ до кроків описаний декларативно.** Кожен екран має `isComplete(state)`. Крок можна відкрити,
  тільки якщо всі попередні завершені. Тому checkout без телефону/email перекидає на відповідний
  крок, а success без підтвердженої бекендом оплати перекидає на checkout. Одне правило для будь-якого флоу.
- **`features/` окремо від `screens/`.** Телефон і email вводяться на одних екранах, а потрібні на
  checkout. Тому вони не можуть «належати» екрану.

## Як додати новий екран

1. Створити папку `src/screens/my-screen/` з компонентом і `index.ts`:

   ```ts
   export const myScreen: ScreenDefinition = {
     key: 'my_screen', // ключ, який приходить з GET /flow
     path: 'my-screen', // URL: /my-screen
     component: lazyWithPreload(() => import('./MyScreen')),
     isComplete: (state) => /* чи можна йти далі */ true, // необов'язково
   }
   ```

2. Додати `myScreen` у масив у `src/screens/registry.ts`.

Усередині компонента для переходу далі: `const { goNext } = useFlowNavigation()`.
Інші екрани, роутер і прогрес-бар міняти не треба. Тексти екрана додаються в `shared/i18n/en.ts`.

## Ключові рішення

### Флоу
- Береться з `?flow=` (без параметра — флоу за замовчуванням), завантажується один раз і зберігається
  в персистентному сторі. Після оновлення сторінки й повернення з оплати повторного запиту немає.
- Відкриття посилання з **іншим** `?flow=` починає нову сесію. Сесія скидається лише після успішного
  завантаження нового флоу, тому посилання з одруківкою не стирає прогрес.
- Невідомі ключі пропускаються (`resolveSteps`). Прогрес, «далі» і «назад» рахуються за списком
  відомих кроків, тому працюють для будь-якого флоу.
- Помилка завантаження показує окремий екран: «такого флоу немає» з кнопкою на дефолтний або
  «не вдалося завантажити» з кнопкою «Спробувати ще».

### Роутинг
- Усі переходи йдуть через `navigate(..., { replace: true })`, тому кроки не потрапляють в історію
  браузера. Повернутися на попередній крок можна внутрішньою кнопкою «назад».
- `search` (наприклад, `?flow=`) передається при кожному переході.

### Стан і персистентність
- Слайси: `flow`, `profile`, `quiz`, `plans`, `payment`. Усі thunks і селектори типізовані через
  `createAppAsyncThunk` / `useAppSelector`, `any` немає (заборонено правилом ESLint).
- Стан пишеться в `localStorage` після кожної зміни і **валідується zod-схемою при читанні**.
  Пошкоджені або застарілі дані просто відкидаються. Чому `localStorage`, а не `sessionStorage`:
  після редіректу на банк повернення інколи відкривається в новій вкладці.
- Відповіді API теж проходять через zod (`shared/api/http.ts`). Типи на межах справжні, а не `as`.

### Оплата
Payment Element працює в режимі **deferred intent**: форма показується одразу з сумою тарифу, а
PaymentIntent створюється тільки після натискання «Pay»:

1. `elements.submit()` перевіряє форму;
2. `POST /payments` з `Idempotency-Key`. Ключ генерується для конкретних planId+email+phone і
   зберігається в сторі **до** запиту. Подвійний клік, оновлення сторінки посеред оплати чи повторна
   спроба після відмови повертають той самий PaymentIntent, нового не створюють;
3. `stripe.confirmPayment({ redirect: 'if_required' })` показує 3DS-вікно або веде на сторінку банку;
4. результат **завжди** береться з `GET /payments/:id`, а відповідь Stripe.js і параметри в URL
   ігноруються. Після повернення з редіректу `paymentId` уже є в сторі, тож перевірка запускається сама.

Стани UI: `idle → submitting → verifying → succeeded | failed | processing (опитування кожні 2 с) | unverified`
(бекенд недоступний, є кнопка «Перевірити статус»). Від подвійного кліку захищають і `condition`
у thunk, і заблокована кнопка.

**Новий платіжний метод** вмикається в Stripe Dashboard, код змінювати не треба: Payment Element
сам показує доступні методи, а `confirmPayment` однаково обробляє модалку, редірект і миттєвий результат.

### Інше
- **Lazy loading:** кожен екран — окремий chunk. Поки користувач на кроці, `StepLayout` заздалегідь
  завантажує наступний (`lazyWithPreload`). Stripe.js завантажується тільки на checkout.
- **Аналітика:** `analytics.track(event)` з типізованим каталогом подій (`screen_view`,
  `payment_succeeded`…), зараз пише в `console.info`. Новий провайдер додається як ще один transport.
- **i18n:** усі тексти лежать у `shared/i18n/en.ts`, тип `Messages` гарантує однакову структуру для
  інших мов.
- **Валідація телефону:** `libphonenumber-js` знає реальні правила нумерації кожної країни і дає
  E.164. Список країн будується з неї ж.
- **Форми:** помилка з'являється тільки після того, як користувач щось ввів і вийшов з поля, або
  після спроби продовжити. Далі вона оновлюється наживо.

## Деплой (Vercel)

Два проєкти з одного репозиторію:

| Проєкт | Root Directory | Змінні середовища |
|---|---|---|
| backend | `backend` | `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`, `CLIENT_ORIGIN=https://<frontend>.vercel.app` |
| frontend | `frontend` | `VITE_API_URL=https://<backend>.vercel.app` |

`frontend/vercel.json` переписує всі шляхи на `index.html`, тому прямі посилання й повернення з
3DS/редіректу на `/checkout` працюють. Ключів у репозиторії немає, лише `.env.example`.
